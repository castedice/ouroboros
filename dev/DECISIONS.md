## DR-009: Meta-Plugin Pivot

**Status:** active
**Date:** 2026-02-14
**Context:** Ouroboros was a "software development plugin" (SDD/TDD/Review workflow). Realized the higher-value purpose is a meta-plugin that generates, researches, and evolves other plugins.
**Decision:** Pivot ouroboros to a meta-plugin. Current SDD-focused assets become the first child plugin. Core capabilities: Generate, Research, Evolve.
**Rationale:**

- The plugin development knowledge accumulated is more valuable as a generative tool
- SDD workflow is one domain among many — personal assistant, research, etc.
- Meta-level enables compound growth across the entire plugin ecosystem
**Consequence:** DR-002, 003, 005, 006, 007 become domain-specific decisions scoped to the Software Development module. Core ouroboros needs new commands/agents for meta-level operations.

## DR-012: Modular Monolith Architecture

**Status:** active
**Date:** 2026-02-17
**Context:** With the meta-plugin pivot (DR-009), needed to decide how to organize domain capabilities — separate plugins or one unified plugin.
**Alternatives considered:**

- Separate repos per plugin — clean separation, but duplicated shared capabilities and no cross-module synergy
- Monorepo with independent plugins — complex build/release, still duplicated
- **Modular monolith (chosen)** — single install, shared capabilities, natural co-evolution
**Decision:** One plugin with domain modules (`core/`, `dev/`, `research/`, `assistant/`). Clear internal boundaries via directory structure and namespaces.
**Rationale:**
- Cross-module synergy: research feeds development, development experience feeds assistant
- Co-Evolution philosophy operates naturally within a single system
- Shared capabilities (brainstorm, compound, cross-validator) without duplication
- If context pollution becomes a problem, internal boundaries make splitting easy
**Consequence:** Updates DR-009 — existing SDD assets become the `dev/` module, not a separate child plugin. Directory restructuring needed for all commands/agents/skills/templates.

## DR-015: Eight Core Capabilities (revised)

**Status:** active
**Date:** 2026-02-17
**Context:** DR-013 defined six capabilities. Further design discussion revealed: Research should cover methodologies and best practices (not just plugin analysis), Generate is modular monolith extension (not standalone plugin creation), third-party plugins should be absorbed into the monolith, sub-module evolution and version upgrades are separate concerns, and Adopt should subsume Setup.
**Decision:** Eight core capabilities:

| Capability | Role |
|------------|------|
| Research | Analyze plugins, development methodologies, and best practices |
| Generate | Extend the modular monolith with new modules |
| Absorb | Absorb third-party plugins into the monolith as modules |
| Evolve | Improve existing sub-modules based on usage and feedback |
| Upgrade | Safe version updates — distinguish built-in, absorbed, and customized content |
| Adopt | Analyze existing project + configure + initialize (subsumes Setup) |
| Onboard | Guide users through features and context-appropriate workflows |
| Evaluate | Assess plugin/module quality (LLM-as-judge + human) |

**Rationale:**

- Research/Generate/Absorb form the **acquisition** lifecycle (learn, create, integrate)
- Evolve/Upgrade form the **maintenance** lifecycle (improve, update safely)
- Adopt/Onboard address **deployment** (fit project, guide user)
- Evaluate is **independent** — used across all phases (pre-Absorb quality check, post-Evolve validation, post-Generate sanity check)
- "Absorb" chosen over "Install" to convey transformation — the plugin is not just added but converted into ouroboros's module format and made part of the system

**Consequence:** Supersedes DR-013. Core module needs commands and agents for all eight capabilities. VISION.md architecture section needs update.

## DR-016: Command Taxonomy — Primitives and Composites

**Status:** active
**Date:** 2026-02-17
**Context:** Designing 8 core commands revealed that some are independent operations while others compose primitives internally.
**Decision:** Commands are classified as **primitives** or **composites**:

| Type | Commands | Description |
|------|----------|-------------|
| Primitive | Research, Generate, Evolve, Evaluate, Brainstorm | Independent, atomic operations |
| Composite | Absorb, Upgrade, Adopt, Onboard | Orchestrate primitives internally |

**Key composites:**

- **Absorb** = Research + Evaluate + Generate/Evolve + decision record
- **Upgrade** = Reconciler-driven merge of ouroboros upstream with user customizations

**Consequence:** Composites reuse primitive agents — no duplicated logic. Absorb has no dedicated agent; it orchestrates researcher → evaluator → generator.

## DR-017: Boundary Rules — Generate / Evolve / Absorb

**Status:** active
**Date:** 2026-02-17
**Context:** Ambiguity around when to use Generate vs Evolve vs Absorb. Edge cases: "add skill to existing module" (evolve or generate?), "reference external plugin and create" (absorb or research+generate?).
**Decision:** Boundary determined by **whether external is involved** and **where the target is**:

- **External involved** → **Absorb** (internally orchestrates Research + Generate/Evolve)
- **No external, target doesn't exist** → **Generate**
- **No external, target exists inside** → **Evolve**
- **Ouroboros self-update** → **Upgrade**

Absorb covers all external-to-internal flows regardless of fidelity (faithful copy vs inspired creation). Evolve covers all internal improvements regardless of origin (built-in, generated, absorbed).

**Consequence:** Both "create based on this reference" and "absorb this" route through `/absorb`. External plugin updates = re-absorb, not upgrade.

## DR-018: Stores — Knowledge, Decisions, Personal

**Status:** active
**Date:** 2026-02-17
**Context:** Needed to decide what artifacts commands produce and where they're stored. Initial design had rigid categories (`plugins/`, `methodologies/`, `patterns/`) plus separate `origins/` and `evolutions/` — too rigid, high cognitive load, and origins/evolutions were fundamentally the same thing (decision records).
**Decision:** Three stores under `docs/`:

| Store | Content | Written by | Read by |
|-------|---------|-----------|---------|
| `docs/knowledge/` | External knowledge (research output) | Research, Absorb | Generate, Absorb, Evolve, Upgrade, Evaluate |
| `docs/decisions/` | Change decision records (absorb + evolve) | Absorb, Evolve | Upgrade |
| `docs/personal/` | Private notes (knowledge + decisions) | User | User |

- **Knowledge**: flat structure, frontmatter tags for classification (no predefined categories)
- **Decisions**: `type: absorb | evolve`, absorb entries include `source` field. Origins and evolutions unified as decision records
- **Personal**: `.gitignore` target, can contain both knowledge and decisions
- Scope distinction: `dev/DECISIONS.md` = ouroboros architectural design (DR-xxx), `docs/decisions/` = module operational changes

**Consequence:** Upgrade reads decision records to understand intent when resolving conflicts. No separate origin/evolution tracking needed.

## DR-019: Upgrade Scope — Ouroboros Self-Update Only

**Status:** active
**Date:** 2026-02-17
**Context:** Initially Upgrade handled both ouroboros updates and external plugin updates. External plugin updates overlap with Absorb (re-absorb with new version).
**Decision:** Upgrade handles **ouroboros self-updates only**. Two scenarios:

| Scenario | Situation | Resolution |
|----------|-----------|------------|
| A. Evolution conflict | ouroboros updates built-in module + user evolved it | Reconcile preserving user's intent from decision records |
| B. Module overlap | User generated custom module + ouroboros ships similar official module | Compare → offer merge/replace/keep choices |

External plugin updates → re-absorb (`/absorb` again with new version).

**Version tracking:** decision entries store `source`, `source-version`, `local-commit`. No git tags (avoids CI/CD pipeline conflicts).

**Consequence:** Upgrade becomes simpler and focused. Reconciler agent handles the merge logic.

## DR-020: Four Fundamental Agents

**Status:** active
**Date:** 2026-02-17
**Context:** Needed to determine shared agent architecture for 8 commands. Initial design had 3 agents (researcher, generator, evaluator) with merger folded into generator. Feedback: reconciliation is a distinct fundamental behavior.
**Decision:** Four fundamental agents:

| Agent | Fundamental behavior | Used by |
|-------|---------------------|---------|
| **researcher** | Analyze and understand | Research, Absorb, Evolve, Adopt |
| **generator** | Create module files from spec | Generate, Absorb, Adopt |
| **evaluator** | Assess quality with criteria | Evaluate, Absorb, Evolve, Generate |
| **reconciler** | Merge/resolve version differences | Upgrade |

**Role separation principle:**

- Command = orchestration (which agents, what order, what input)
- Agent = execution (one specialized behavior, done well)
- Skill = knowledge (methodology/criteria that agents reference)

**Subdivision roadmap:** Start with 4 fundamental agents. Subdivide when `/evaluate` identifies specialization needs:

- researcher → plugin-analyzer, codebase-scanner, methodology-researcher
- generator → scaffolder, config-generator
- evaluator/reconciler → remain single (evaluation criteria in skills, not agents)

**Consequence:** 4 agents cover 8 commands. Absorb uses researcher → evaluator → generator (no dedicated absorb agent).

## DR-021: Implementation Order — Evaluate First, Self-Improvement Early

**Status:** active
**Date:** 2026-02-17
**Context:** Default order (Research → Generate → ...) delays the feedback loop. Evaluate is cross-cutting and independent — building it first enables quality assessment of every subsequent command. The ouroboros philosophy demands the self-improvement cycle start as early as possible.
**Decision:** Implementation order prioritizes the self-improvement loop:

| Order | Command | Agent(s) built | Milestone |
|-------|---------|---------------|-----------|
| 1 | `/evaluate` | evaluator | Can assess quality of existing dev module |
| 2 | `/evolve` | researcher | **Self-improvement cycle ON** — evaluate + evolve on dev module |
| 3 | `/research` | (researcher reused) | External learning added to the cycle |
| 4 | `/generate` | generator | Creation ability |
| 5 | `/absorb` | (composite) | Full acquisition pipeline |
| 6 | `/upgrade` | reconciler | Self-update |
| 7 | `/adopt`, `/onboard` | (orchestration only) | Deployment |

**Rationale:**

- "You can't improve what you can't measure" — evaluate first
- Milestone 2 (evaluate + evolve) enables ouroboros to improve its own dev module commands/agents
- Existing dev module (9 commands, 10 agents) provides immediate material for the self-improvement cycle
- Each subsequent command is quality-checked by `/evaluate` as it's built

**Consequence:** The serpent starts eating its tail at step 2, not at the end.

## DR-022: Evaluate — Two-Axis Evaluation with Additive Scoring

**Status:** active
**Date:** 2026-02-17
**Context:** Designing the `/evaluate` command's evaluation framework. Need to choose scoring method, criteria structure, and evaluation modes.
**Decision:**

1. **Two axes**: Static (definition file quality) + Dynamic (output/result quality). Static applies to all 5 types; dynamic applies to 4 (CLAUDE.md excluded — no runtime output concept).

2. **Scoring**: Additive binary (0/1 × 5 criteria per type). Based on LLM-as-judge research — simplest, most reliable, and provides specific per-criterion feedback.

3. **Overall Level**: 4-tier (5→Excellent, 4→Good, 2~3→Needs Work, 0~1→Poor). Natural mapping from 5-point sum.

4. **Pairwise comparison**: Two independent evaluations + one position-swapped comparison. Mitigates position bias at 3x cost (acceptable for quality-critical before/after checks).

5. **Criteria location**: Skill (`skills/core/evaluation/SKILL.md`) contains philosophy and scoring rules. Per-type criteria in `references/` subdirectory (progressive disclosure pattern from knowledge base research).

6. **Evaluator agent**: opus model, read-only tools `[Read, Grep, Glob]`. Complex reasoning requires opus; minimum privilege prevents accidental modification.

7. **Four modes**: Single Static (A), Module Scan (B), Before/After (C), Output (D). Covers all evaluation use cases from spot-check to comprehensive audit.

**Rationale:**

- Additive scoring outperforms Likert scales for LLM judges (30% better human agreement per research)
- Separation of static/dynamic criteria enables independent evolution of each axis
- Progressive disclosure keeps skill compact while providing deep criteria when needed
- Read-only evaluator enforces separation of concerns (evaluate ≠ fix)

**Consequence:** First core capability implemented. Enables quality assessment of all subsequent commands/agents as they're built.

## DR-023: Evolve — Command-Driven Apply with Agent Analysis and Validation

**Status:** active
**Date:** 2026-02-17
**Context:** Designing the `/evolve` command — second core capability after `/evaluate`. Key design question: who performs the "apply" step (actual file modification)?

**Decision:**

1. **Apply ownership**: The evolve **command itself** applies changes (Edit/Write tools). Agents remain read-only:
   - researcher (read-only) → analyzes weaknesses, proposes improvements
   - evolve command (Edit/Write) → applies changes with user confirmation
   - evaluator (read-only) → validates before/after

2. **Six-phase workflow**: Baseline → Analysis → Planning → Apply → Validate → Record

3. **Quality gate**: Before/after evaluation with three verdicts:
   - `improved` → accept changes, record decision
   - `lateral` → ask user whether to keep changes
   - `degraded` → rollback or retry with different approach (max 2 retries)

4. **Two modes**: Single Component (A) and Module Focus (B — evolve weakest component first)

5. **Researcher agent**: New core agent (`agents/core/researcher.md`). Read-only, opus model. Performs root cause analysis on evaluation results and searches knowledge base for applicable patterns.

6. **Evolution skill**: `skills/core/evolution/SKILL.md` provides improvement prioritization methodology (0-score criteria > [HIGH] > [MED] > [LOW]) and bias mitigation strategies.

7. **Decision entries**: Evolve produces `docs/decisions/{date}-evolve-{name}.md` recording background, decisions, changes, and verification results.

**Rationale:**

- Command-as-applier matches the evaluator v1→v3 prototype pattern (proven in previous session)
- Keeps agent count at 4 (DR-020) — researcher added, no "improver" agent needed
- Read-only agents + write-capable command = clear separation of concerns
- User checkpoint at Planning phase prevents unwanted changes
- Quality gate with regression check ensures no criteria degrades during improvement

**Consequence:** Second core capability implemented. Combined with `/evaluate`, enables the self-improvement cycle: evaluate → evolve → evaluate. Researcher agent is reusable by future commands (/research, /absorb, /adopt).

## DR-024: 2-Phase Execution Model with Git Worktree Isolation

**Status:** active
**Date:** 2026-02-18
**Context:** Users want "turnkey" execution — give a requirement, get a result, review only at the end. Current commands have multiple mid-workflow checkpoints (Phase 2 "Proceed?", Phase 4 "Confirm plan?", Phase 5 "Store?") that require constant user attention. Additionally, running multiple commands in parallel is impossible because they share a single working tree.

**Decision:**

1. **2-Phase Execution Model**: All core commands follow Autopilot → Review:
   - **Autopilot phase**: Command runs end-to-end without user interaction. All analysis, generation, file modifications happen automatically. Mid-workflow checkpoints are removed.
   - **Review phase**: Final result summary + pending actions presented to user. User approves (merge), edits, or discards (worktree removed).

2. **Git worktree isolation**: Each command execution gets its own worktree:

   ```bash
   git worktree add {worktree-path} -b ouroboros/{cmd}/{target} HEAD
   ```

   - All file changes happen inside the worktree, main working tree stays clean
   - Multiple commands can run in parallel (each in its own worktree)
   - Review uses `git diff main..ouroboros/{cmd}/{target}`
   - Approve: squash merge to main + worktree cleanup
   - Reject: `git worktree remove` + `git branch -D`

3. **Worktree path convention**: `{repo}/.worktrees/{cmd}-{target}/` (gitignored)

4. **Per-command autopilot boundaries**:

   | Command | Autopilot | Review shows |
   |---------|-----------|-------------|
   | /evaluate | Full (read-only, no file changes) | Report only |
   | /research | Phase 1-4 auto, write entry in worktree | Draft entry + "save?" |
   | /evolve | Phase 1-7 auto (includes file modification + validation) | Before/after score + diff + decision entry |
   | /generate | Full (create all files in worktree) | Generated file list + preview |

5. **Auto-retry on degraded evolution**: If /evolve validation returns "degraded", auto-rollback and retry once with failure context. After 2 consecutive failures, stop and report in review phase.

6. **Permission configuration**: `acceptEdits` mode + comprehensive allow/deny lists in settings.json. PreToolUse hooks as dynamic safety net. No mid-workflow permission prompts.

   ```json
   {
     "permissions": {
       "allow": ["WebSearch", "WebFetch", "Bash(gh *)", "Bash(git *)", "Task"],
       "deny": ["Bash(rm -rf *)", "Bash(sudo *)", "Bash(git push *)", "Bash(git reset --hard*)"]
     }
   }
   ```

7. **Team integration**: Worktree model naturally fits Claude Code teams — each teammate works in their own worktree, team lead reviews and merges from main.

**Rationale:**

- Git worktree provides perfect isolation without copying files — lightweight and native to git
- Squash merge keeps main history clean regardless of intermediate worktree commits
- `acceptEdits` + allow/deny + hooks creates "safe YOLO" — autonomous but bounded
- Parallel execution enables future composite commands (/absorb = /research + /evaluate + /evolve in parallel worktrees)
- Pattern aligns with OMC's Team Mode (see `docs/knowledge/oh-my-claudecode-orchestration-patterns.md`) but uses git worktree instead of custom state management

**Consequence:** Commands must be refactored to accept a worktree path parameter and operate relative to it. settings.json needs allow/deny expansion. `.worktrees/` must be added to .gitignore. Implementation order: settings.json hardening → command refactor (/research first, simplest) → /evolve → /generate.

## DR-025: /generate Scope Expansion — Module + Component Level

**Status:** active
**Date:** 2026-02-18
**Context:** During /absorb design, discovered that `/generate` only supports full module creation. Cannot add a single component (command, agent, skill) to an existing module. This limitation blocks the Integrate mode of /absorb and is generally useful for incremental module growth.

**Decision:** Extend `/generate` to support two modes, auto-detected from arguments:

| Input pattern | Condition | Mode | Action |
|---------------|-----------|------|--------|
| `<module-name> "desc"` | Module doesn't exist | Mode A: Module Generation | Create full module (existing behavior) |
| `<module>/<name> "desc"` | Module exists | Mode B: Component Generation | Add single component to existing module |

**Mode detection logic:**

1. If argument contains `/` → split into `module` + `component-name`, verify module exists → Mode B
2. If argument has no `/` → verify module doesn't exist → Mode A
3. Edge cases: module exists + no `/` → error ("Use `/evolve` or specify component path"); module doesn't exist + has `/` → error ("Module doesn't exist. Use `/generate <module> \"desc\"` to create it first")

**Component type determination (Mode B):**

- Inferred from description keywords (e.g., "command that...", "agent for...", "skill about...")
- Explicit override: `--type <command|agent|skill|template>`
- Default: `command` (most common use case)

**Mode B context gathering (Phase 2):**

- 2a: Read all existing module components (pattern extraction)
- 2b: Knowledge base scan (same as Mode A)
- 2c: Load evaluation criteria for the target component type
- 2d: Select 1-2 existing components of the same type as reference

**Mode B execution differences:**

- Phase 3: Generator uses Procedure 3 (Component Generation) instead of Procedure 1
- Phase 5: Single file written to worktree (not full module scaffold)
- Phase 6: Single component evaluation (not full module scan)
- Phase 7-9: Same structure, scoped to single component

**Rationale:**

- Incremental growth is the normal path — modules rarely appear complete in one shot
- `/evolve` improves existing components; `/generate` creates new ones — orthogonal operations
- Mode detection from argument pattern is intuitive: `research` vs `research/literature-review`
- Reuses existing worktree/evaluation infrastructure from DR-024

**Consequence:** Generator agent needs a new Procedure 3 (Component Generation). /generate command gains Mode B phases. /absorb Integrate mode can delegate component creation to `/generate <module>/<name>`.

## DR-027: Multi-model Integration — Direct Bash Invocation

**Status:** active
**Date:** 2026-02-19
**Context:** Phase 2 Multi-model Routing requires invoking external model CLIs (Gemini CLI, Codex CLI) from within ouroboros commands. Three approaches considered: (1) Direct Bash invocation, (2) MCP Server Bridge, (3) Hybrid (Bash + MCP).

**Decision:** Direct Bash invocation with structured prompt relay.

| Approach | Pros | Cons |
|----------|------|------|
| **Direct Bash (chosen)** | Zero infrastructure, bundleable in plugin, works with settings.json allow patterns (`Bash(gemini *)`) | Fragile to CLI flag changes, manual output parsing |
| MCP Server Bridge | Structured tool interface, conversation history | Requires per-user `claude mcp add` setup, cannot be bundled in plugin.json |
| Hybrid (Bash + MCP) | Best of both worlds | Two code paths to maintain, premature complexity |

**Key factors:**

1. Background Task agents cannot access Bash — multi-model calls MUST happen at command level regardless of approach. MCP's agent-level advantage is moot.
2. Plugin.json cannot configure MCP servers. Bash requires only CLI installation.
3. Framing bias is mitigated by prompt relay design (raw content relay), not by architecture choice.
4. Both Gemini CLI (`gemini -p --output-format json`) and Codex CLI (`codex exec --json`) support structured JSON output.

**Consequence:** Commands using multi-model must include `Bash` in `allowed-tools`. User's settings.json must allow `Bash(gemini *)` and `Bash(codex *)`. Invocation protocol documented in `skills/core/routing/references/invocation-protocol.md`.

**Maintenance note:** Gemini CLI and Codex CLI are both rapidly evolving (weekly/daily releases). CLI flags, model IDs, output formats, and available models change frequently. The invocation protocol (`references/invocation-protocol.md`) and routing table (`references/routing-table.md`) must be periodically verified against the latest official documentation and updated when discrepancies are found. Always record CLI versions when testing.

**Alternative approaches catalogue** (recorded for future re-evaluation):

| Approach | How | Pros | Cons | When to Reconsider |
|----------|-----|------|------|-------------------|
| **CLI pipe (current)** | `heredoc \| codex exec --json -` | Zero infra, plugin-bundleable, UNIX composable | CLI flag churn, shell escaping, output parsing fragile | — (current choice) |
| **REST API direct** | `curl`/`xh` to OpenAI/Google REST endpoints | Full parameter control, no CLI dependency, cost-efficient | API key management, auth complexity, manual request construction | CLI becomes too unstable or adds unwanted overhead |
| **OpenAI Codex SDK** (TypeScript) | `import { Codex } from "@openai/codex-sdk"` | Thread reuse, stateful, programmatic error handling, resumeThread | Node.js dependency, can't call from plugin commands (Bash only) | If hooks/scripts gain Node.js runtime, or ouroboros adds a script layer |
| **Google AI SDK** (Python/Node) | `import google.generativeai` | Structured API, streaming, function calling | SDK dependency, can't call from plugin commands | Same as Codex SDK |
| **MCP Server Bridge** | Wrap external models as MCP tools, `claude mcp add` | Structured tool interface, conversation history, agent-level access | Per-user setup required, not bundleable in plugin.json, extra process | If plugin.json gains MCP server configuration support |
| **Daemon pattern** | Background process (claude_code_bridge style: `caskd`/`gaskd`) | Process reuse, queueing, context isolation, lower startup overhead | Complex lifecycle management, port conflicts, process cleanup | High-frequency multi-model calls (10+ per command run) |
| **LLM abstraction layer** | Simon Willison's `llm` CLI, LiteLLM proxy | Unified interface across providers, plugin ecosystem | Extra dependency, abstraction leakage, may not support all features | If ouroboros needs 4+ providers or frequent provider switching |
| **Claude sub-process** | Spawn `claude` CLI with different system prompt / plugin context | Same tool ecosystem, no new dependency | No direct model control, heavy process, prompt injection risk | Need Claude-to-Claude delegation with different personas |

**Ecosystem validation (2026-02):** claude-octopus (CLI pipe, 3-provider consensus), myclaude (CLI pipe, 2-tier), claude_code_bridge (daemon), opencode-model-router (prompt injection routing). All active projects chose CLI-level integration over SDK/MCP, confirming the current approach aligns with community practice. SDK approach is theoretically superior but blocked by plugin architecture constraints.

## DR-029: Consensus Protocol — Independent Scoring with Majority Rule

**Status:** active
**Date:** 2026-02-19
**Context:** When multiple models score the same component, how to integrate their results? Options: (1) average scores, (2) majority rule per criterion, (3) weighted scoring (model-specific weights), (4) unanimous requirement.

**Decision:** Independent scoring (no model sees others' results) + majority rule per criterion + self-enhancement bias flagging. Unanimous convergence as quality sub-mode.

**Three integration modes:**

| Mode | When | Protocol |
|------|------|----------|
| A: Cherry-pick | Breadth tasks (research, extraction) | Claude selects best output |
| B: Consensus | Scoring tasks (evaluation, comparison) | Independent scoring + majority/unanimous rule |
| C: Synthesis | Multi-faceted tasks (architecture, gap analysis) | Combine strongest aspects |

**Consensus (Mode B) — two sub-modes:**

1. **Majority rule (fast, default)**: Each model scores independently → per-criterion majority vote → divergence analysis
2. **Unanimous (quality, `--unanimous`)**: Same start → divergence triggers convergence loop (share reasoning, ask for reconsideration, max 2 iterations) → escalate to user if still divergent

**Shared specifics:**

- No model sees others' results during initial scoring (prevents anchoring)
- 2-model split → Claude as tiebreaker (majority) or user escalation (unanimous)
- Self-enhancement bias detection: when Claude scores 1 and ALL external models score 0, flag in report
- Agreement rate interpretation: 100%=high confidence, 60%=moderate (recommend human review), <40%=unreliable

**Rationale:**

- Independent scoring is the gold standard in LLM-as-judge literature for reducing inter-model bias
- Majority rule is simple, transparent, and works well with binary (0/1) scoring
- Self-enhancement bias (~10% per research) is a known risk when Claude evaluates its own output
- Agreement rate provides meta-confidence: low agreement signals ambiguous criteria or boundary quality

**Consequence:** Evaluation reports gain multi-model section with per-model scores, divergence analysis, and agreement rate. Documented in `skills/core/routing/references/consensus-protocol.md`.

## DR-030: Multi-model as Opt-in — `--multi` Flag

**Status:** active
**Date:** 2026-02-19
**Context:** Should multi-model routing be the default behavior or opt-in? Factors: cost (1.3-2.5x multiplier), external CLI dependency, graceful degradation, user expectations.

**Decision:** Opt-in via `--multi` flag on supporting commands. Default behavior unchanged (single-model, Claude only).

**Rationale:**

1. **Cost**: Token cost multiplies 1.3x (2 models) to 2.5x (3 models). Module scan with N components × 3 models adds up fast.
2. **Dependency**: Gemini CLI and Codex CLI are external tools that may not be installed. Defaulting to multi-model would cause warnings on every invocation for users without external CLIs.
3. **Speed**: External CLI calls add 10-30 seconds per invocation (network round-trip + model inference).
4. **Baseline preservation**: Users should be able to get fast, cheap, single-model results by default. Multi-model is for when additional confidence is worth the cost.
5. **Graceful degradation**: When `--multi` is requested but no external CLIs are available, falls back to single-model with an informational message — never errors out.

**Implementation:**

- Phase 2b: `/evaluate --multi`
- Phase 2c candidates: `/evolve --multi`, `/research --multi`, `/generate --multi`
- Each command gates multi-model code paths on the `--multi` flag check

**Consequence:** All multi-model code is additive — no existing behavior changes. Users discover multi-model when ready. Documentation and `/onboard` mention `--multi` as an advanced option.

## DR-031: Separation of Concerns — Command/Skill/Script Layering

**Status:** active
**Date:** 2026-02-20
**Context:** Phase 2b SoC refactoring proved the value of extracting inline logic from commands. The `evaluate.md` refactoring (100+ lines of inline Bash → `invoke-model.sh` + `parsing-strategy.md`) reduced command complexity and made the parsing logic independently testable and evolvable. A systematic audit revealed 6 major DRY violations across the codebase, all stemming from commands embedding implementation details that belong in scripts or skills.

**Decision:** Formalize the three-tier Separation of Concerns principle and commit to systematic extraction.

### The Three-Tier Principle

| Layer | Role | Concern | Example |
|-------|------|---------|---------|
| **Command** | Orchestration | **What** to do and **when** | "Phase 4: Create worktree, Phase 6: Run quality gate" |
| **Skill** | Knowledge | **How** to do it (methodology) | Quality gate threshold, retry policy, evaluation criteria |
| **Script** | Execution | **Do** it (mechanical) | `worktree.sh create`, `invoke-model.sh`, `format.sh` |

**Diagnostic question:** "Is this logic the command's concern, or a script/skill's concern?" If the same logic appears in 2+ commands, it belongs in a shared layer.

### Identified Violations (6 patterns, ordered by severity)

| # | Pattern | Locations | Duplication | Target Layer |
|---|---------|-----------|-------------|--------------|
| 1 | Git worktree lifecycle (create/merge/discard/cleanup) | generate, evolve, absorb, research, upgrade | 95% identical across 5 commands | **Script**: `scripts/worktree.sh` |
| 2 | Worktree error cleanup | generate, evolve, absorb, upgrade | 100% identical across 4 commands | **Script**: merged into `worktree.sh` |
| 3 | Quality gate loop (evaluate→threshold→retry→re-evaluate) | generate, absorb | 85% identical structure | **Skill**: quality gate procedure reference |
| 4 | Review & merge/discard phase | generate, evolve, absorb, research, upgrade | 70% structural overlap | Acceptable — command-specific context varies enough |
| 5 | Format hooks (input parse, extension check, tool run) | format-python.sh, format-typescript.sh, format-rust.sh | 90% identical boilerplate | **Script**: `scripts/format.sh` unified |
| 6 | Decision entry recording | generate, evolve, absorb, research, upgrade | 60% structural overlap | Acceptable — each type has distinct required fields |

### Extraction Plan

**Phase A (P0): `scripts/worktree.sh`** — Consolidate worktree lifecycle into a single script.

- Interface: `worktree.sh {create|commit|merge|discard|cleanup} <args>`
- Covers: creation (with branch conflict handling), commit, squash merge, discard, error cleanup
- Commands replace 10-15 lines each with single-line script calls
- Error cleanup consistency guaranteed across all 5 commands

**Phase B (P1): Quality gate as skill reference** — Extract the evaluate-retry loop into a skill procedure.

- Location: `skills/core/validation/references/quality-gate-procedure.md`
- Covers: threshold (>= 3/5), retry policy (max 1 round), failure behavior (log and proceed)
- Commands reference the procedure: "Apply quality gate (see quality-gate-procedure)"

**Phase C (P2): `scripts/format.sh`** — Unify format hooks into a single dispatcher.

- Interface: single script with extension-based routing
- Replaces 3 near-identical scripts with one

**Not extracted (acceptable duplication):**

- Review phase (#4): Command-specific context (scores, diffs, mode info) varies enough that extraction would create a leaky abstraction
- Decision entry (#6): Each command type has distinct required fields; a meta-template would be over-engineering

### Validation Criteria

Each extraction must satisfy:

1. **Commands get simpler** — fewer lines, clearer orchestration flow
2. **No behavior change** — before/after functional equivalence
3. **Independent evolvability** — extracted script/skill can be improved via `/evolve` without touching commands
4. **Error handling improves** — centralized cleanup is more reliable than 5 separate implementations

**Rationale:**

- The `invoke-model.sh` extraction (Phase 2b) proved this pattern: 100+ inline lines → 1-line delegation, with independent testability and 3-tier fallback
- DRY principle: identical logic in 5 places means a bug fix requires 5 edits — fragile and error-prone
- Worktree cleanup inconsistency is already visible: research.md lacks explicit error cleanup while others have it
- Phase 1 retrospective established consistent command structure; SoC extraction is the natural next step for internal consistency

**Consequence:** Three extraction phases produce 2 new scripts and 1 new skill reference. Commands become shorter and more focused on orchestration. Future worktree or quality gate changes require editing only one file instead of 5.

## DR-032: Markdown Lint Convention — rumdl Configuration

**Status:** active
**Date:** 2026-02-20
**Context:** Phase C introduced rumdl as the markdown linter. A codebase-wide lint pass (99 files, 629 initial issues) required deciding which rules to enforce and which to disable for our AI prompt/instruction files.

**Decision:** Configure `.rumdl.toml` with project-appropriate rule disabling. Use `rumdl check` (report-only) in format hooks, not `rumdl fmt` (auto-fix), because auto-fix makes wrong choices for MD040 (adds `text` to all untagged code blocks).

**Disabled rules:**

| Rule | Reason |
|------|--------|
| MD013 | Line length — AI prompt files are not constrained to terminal width |
| MD033 | Inline HTML — `<placeholder>` syntax used in argument-hint frontmatter |
| MD036 | Emphasis as heading — SKILL.md motto pattern (`*"Quote"*`) is intentional design |
| MD041 | First line h1 — agents/templates start with YAML frontmatter, not headings |
| MD056 | Table column count — templates use `|` in placeholders (e.g., `${A | B | C}`) |

**Code fence conventions:**

- All code blocks use backticks (`` ` ``), never tildes (`~`)
- Nested code blocks: outer uses ```` (4 backticks), inner uses ``` (3 backticks)
- MD048 enforced (re-enabled after removing all `~~~` usage)
- MD040 enforced — every code block must have a language tag (`bash`, `markdown`, `json`, `text`, `yaml`, `toml`)

**Rationale:**

- Disabled rules all stem from intentional patterns in our plugin file format, not mistakes
- `rumdl check` over `rumdl fmt`: auto-fix for MD040 cannot determine correct language tags — only the author (AI or human) can judge whether a code block is `bash`, `markdown`, or `text`
- 4-backtick nesting is the markdown spec standard, simpler than mixing ``` and ~~~

**Consequence:** All 99 markdown files pass `rumdl check` with zero issues. Format hook reports violations for human/AI review. New files must follow these conventions.

## DR-034: Tiered Binary Criteria — Score Inflation Mitigation

**Date:** 2026-02-20
**Status:** In Progress (Agent type designed, 4 types remaining)
**Context:** Binary (0/1) criteria yield 5/5 too easily because they check "existence" not "quality". All current criteria are threshold-based existence checks. Research confirmed: root cause is WHAT we measure, not HOW we score.

**Decision:** Keep binary scoring but add higher-difficulty tiers:

- **Tier 1 — Foundation (F)**: Existing 5 criteria per type, unchanged. "Does it exist?"
- **Tier 2 — Craft (Q)**: 5-8 new criteria per type. "Is it well-made?"
- **Tier 3 — Excellence (E)**: 2-4 new criteria per type. "Is it exemplary?"

Severity gate (SonarQube-inspired): Foundation failures cap maximum achievable level regardless of Craft/Excellence scores.

**Alternatives Rejected:**

- **4-point rubric (0-3)**: LLM agreeableness bias (TPR 96%, TNR <25%) shifts inflation to 2/3. Ambiguous middle levels where LLM judges are least reliable. Source: arXiv 2510.11822, arXiv 2601.03444
- **Hybrid (binary + rubric)**: Two scoring systems → complexity for evaluator agent, inconsistent judgment modes
- **Criteria count increase without tiers**: Flat list of 15 criteria loses the severity-gate benefit — many easy wins can mask major gaps

**Rationale:**

- Binary has best inter-rater reliability (confirmed across multiple studies: SelfCheckGPT, MT-Bench)
- Inflation problem is about measurement target, not scale granularity — adding quality-focused criteria directly addresses root cause
- SonarQube severity-gate prevents gaming: Foundation 5/5 is prerequisite for Level 3+
- CMMI model validates: quality levels represent capability type changes (exist → well-made → exemplary), not numeric increments

**Consequence:** Total criteria per type increases from 5 to 12-17. Evaluation cost increases proportionally but each judgment remains binary (fast). Components previously at 5/5 will spread across Levels 2-4, enabling meaningful evolution tracking. See `docs/knowledge/evaluation-scoring-design.md` for full research, `dev/tiered-criteria-draft.md` for Agent type design.

## DR-035: Evaluation Model Selection — Evidence-Based Routing

**Date:** 2026-02-20
**Status:** active
**Context:** Phase 4 Step 2. The default external model config for `--multi` evaluation was gpt-5.2 xhigh + Gemini auto, chosen theoretically. Needed empirical validation: does xhigh reasoning help? Can cheaper models maintain discrimination? Is Gemini useful for evaluation?

**Experiment:** 48 invocations across 12 configs × 2 benchmarks (evaluate.md command, evaluator.md agent) × 2 runs. Includes supplementary round: gpt-5.3-codex medium/xhigh and gemini-3-pro-preview. Gemini 3.1 re-experiment (G6, 4 invocations) added 2026-02-28. Full results + qualitative analysis in `dev/experiments/model-optimization/`.

**Key Findings:**

1. **Codex discrimination is strong and consistent**: All Codex configs correctly identify E1 (SoC Purity) and E2 (Context Efficiency) as 0 — both are known backlog items confirmed by project STATUS.md. Foundation (F1-F5) and Craft (Q1-Q7) are unanimously 1 across all configs and effort levels.
2. **xhigh effort is consistently strict, not over-strict**: xhigh always scores E4=0 (consistent), while high/medium fluctuate between 0 and 1 across runs (non-deterministic on borderline criteria). Qualitative analysis of E4 reasoning shows both interpretations are valid — xhigh reads criteria literally ("placeholders are not context-populated"), high reads pragmatically ("placeholders intended to be populated at runtime"). Higher score ≠ better judgment.
3. **gpt-5.3-codex matches gpt-5.2 discrimination at 1.5-2.6× speed**: Identical 0-score patterns across all effort levels. No coding-model bias detected in reasoning — references to "Bash commands" and "JSON schemas" reflect actual evaluate.md content, not model prejudice. E1/E2 reasoning is substantively identical between models.
4. **Gemini (G1-G4) lacks discrimination entirely**: Systematic 16/16 scoring. Reasoning is factually incorrect — G1 calls evaluate.md a "pure orchestrator" and "extremely token-efficient" despite 35KB of inline implementation. Only gemini-3-pro-preview (G5) shows E1 discrimination with specific evidence ("Phase 5.5 embeds voting algorithms, convergence rules, bias detection").
5. **gemini-3-pro-preview is the only viable Gemini (pre-3.1)**: E1=0 on evaluate.md with precise reasoning. However still lenient on E2 and evaluator. 429 capacity issues did not occur during experiment (previously chronic).
6. **gemini-3.1-pro-preview (G6, 2026-02-28) shows dramatic improvement**: E1=0 on evaluate.md 100% (2/2 runs, vs G5's 50%). E2=0 in 50% of runs (vs G5's 0%). Novel E3=0 finding with valid reasoning. Evidence-based, specific reasoning quality ("'which codex' availability checks", "uuidgen string manipulations"). Still lenient on evaluator.md (16/16 both runs). Viable as periodic spot-checker but E2 consistency insufficient for consensus participation.
7. **C5 (spark) unsupported**: Requires ChatGPT Pro research preview access.
8. **Parse stability**: Codex 100% (24/24 exit 0 across all configs). Gemini pre-3.1: 87.5% (14/16; 1 parse failure, 1 non-standard format). Gemini 3.1: 100% (4/4).

**Decision:**

- **Codex for evaluation**: `gpt-5.3-codex` with `xhigh` reasoning effort (was: gpt-5.2 xhigh). Same consistency but 2.6× faster (94s vs 249s). The coding model shows no bias disadvantage on non-code evaluation and delivers identical discrimination. xhigh provides deterministic judgment on borderline criteria — important for reproducible evaluation baselines.
- **Gemini for evaluation**: `gemini-3.1-pro-preview` viable as periodic spot-checker (was: excluded). E1 discrimination 100%, E2 50%, evidence-based reasoning. Not added to `--multi` consensus due to E2 inconsistency — use for quarterly spot-checks on sample components.
- **Fast screening config**: `gpt-5.3-codex` with `medium` for regression suite bulk evaluation. Same E1/E2 discrimination, E4 fluctuates, 2× faster than xhigh (45s).

**Alternatives Considered:**

- **gpt-5.2 high (initial DR-035)**: Same accuracy as gpt-5.3-codex but 1.6× slower. Non-deterministic on E4. Qualitative reasoning analysis revealed that "higher score = better" assumption was flawed — xhigh's lower score reflects stricter but valid interpretation, not worse judgment.
- **gpt-5.3-codex high**: Viable middle ground (65s, same E1/E2 accuracy). But E4 fluctuation makes it non-reproducible — undesirable for baselines.
- **Keep Gemini as optional leniency cross-check**: Pre-3.1 Gemini reasoning quality (factually incorrect on E1/E2) adds noise. 3.1 is viable for spot-checks but E2 inconsistency (50%) prevents consensus participation.

**Methodology note:** "Higher overall score" does not indicate a better evaluator. Evaluation quality is measured by: (1) agreement with confirmed ground truth (E1=0, E2=0), (2) reasoning specificity (does it cite concrete evidence?), (3) consistency across runs, (4) factual accuracy of reasoning claims.

**Consequence:** Default evaluation routing: `gpt-5.3-codex xhigh`. Regression/bulk: `gpt-5.3-codex medium`. Gemini: `gemini-3.1-pro-preview` for periodic spot-checks (not consensus). Self-evaluation bias analysis: `dev/experiments/self-eval-bias/analysis.md`.

## DR-039: SWE Module — Naming and Structure

**Date:** 2026-02-22
**Status:** active
**Context:** Phase 5 begins. The first domain module needs naming, command structure, and pipeline design. Previously called "Dev Module" with skeleton commands (plan, work, review, compound, spiral) from the pre-pivot era. All 32 legacy files archived to `dev/archive/`.

### Module Name: `swe`

**Decision:** Module is named `swe` (Software Engineering), not `dev`.

**Rationale:**

- `develop` shortened to `dev` is the natural name for the implementation composite command
- Using `dev` for both module and command would create `/dev dev` collision
- `swe` is widely recognized in the tech industry (Software Engineer = SWE)
- More encompassing than `dev` — covers the full engineering lifecycle, not just development

### Pipeline: Invariant Stages, Variable Depth

**Decision:** Fixed 8-stage pipeline with variable depth per stage.

The pipeline is invariant — every task traverses the same sequence. Only the depth at each stage varies (Skip / Light / Standard / Deep). This is inspired by the medical diagnosis analogy: the cognitive sequence is always the same, the effort adapts to severity.

| # | Stage | Purpose | Key Output |
|---|-------|---------|------------|
| 1 | **Understand** | Analyze requirements, domain modeling, existing code | Context Document |
| 2 | **Constrain** | Enumerate constraints and boundaries | Constraint Profile |
| 3 | **Design** | Architecture, algorithm/data structure selection, structural decisions | Architecture Spec |
| 4 | **Interface** | Define contracts between components | Interface Contracts |
| 5 | **Test** | Write tests against interfaces (TDD Red phase) | Test Suite |
| 6 | **Implement** | Write code to pass tests (TDD Green phase) | Source Code |
| 7 | **Verify** | Broader validation — integration, acceptance, manual verification | Verification Report |
| 8 | **Optimize** | Profiling-driven tuning, refactoring (TDD Refactor phase) | Optimization Report |

**Design vs Optimize boundary:** Design stage makes the big algorithmic decisions (data structure selection, algorithm choice, performance characteristics). Optimize stage does post-implementation fine-tuning based on profiling — not wholesale redesign.

**Depth levels:**

- **Skip**: Stage not applicable
- **Light**: Minimal (inline notes, minutes)
- **Standard**: Structured document (template-based, hours) — default
- **Deep**: Comprehensive with diagrams and alternatives analysis (hours-days)

### Command Structure: Primitives + Composites + Meta-composite

**Decision:** Follow the ouroboros core pattern (DR-016) — primitives compose into composites, composites compose into meta-composite.

**Primitives** (8 individual commands, each independently executable):

- `/swe understand`, `/swe constrain`, `/swe design`, `/swe interface`
- `/swe test`, `/swe implement`, `/swe verify`, `/swe optimize`

**Composites** (4 grouped commands):

| Composite | Composes | Naming Origin |
|-----------|----------|---------------|
| `/swe spec` | understand + constrain + design + interface | "Specification" — SDLC terminology |
| `/swe dev` | test + implement + verify + optimize | "Develop" — TDD cycle (Red → Green → Verify → Refactor) |
| `/swe ship` | integration test + security review + code review + deploy | "Ship" — universal tech term for release |
| `/swe tune` | evaluate + improve + retrospect | "Tune" — fine-tuning, calibration |

**Meta-composite** (1 turnkey command):

- `/swe spiral` = spec → dev → ship → tune (one full spiral)

**Ouroboros cycle connection:**

```text
spec → dev → ship → tune
  ↑                    ↓
  └────────────────────┘  (spiral: each turn elevates the next)
```

`tune` is the ouroboros connection point — it evaluates and improves what was built, feeding learnings back into the next `spec` cycle. The name `spiral` reflects that each iteration is not mere repetition but upward progression.

### Naming Rationale

| Name | Register | Why chosen |
|------|----------|------------|
| spec | Engineering | "Spec it" is natural engineering speak; avoids `plan` conflict with Claude Code plan mode |
| dev | Engineering | Short for develop; the most common daily activity |
| ship | Tech industry | "Ship it" — universally understood as releasing software |
| tune | Engineering | "Fine-tune" — improvement/calibration; short and matches register |
| spiral | SW Engineering | Boehm's spiral model — iterative development with upward progression; ouroboros feedback loop |

### Three Foundational Methodologies: SDD + TDD + DDD

The pipeline embodies three established software engineering methodologies, each owning specific stages:

| Methodology | Pipeline Stages | Core Contribution |
|-------------|----------------|-------------------|
| **DDD** (Domain-Driven Design) | Understand, Design | Domain modeling, ubiquitous language, bounded contexts — ensures we solve the right problem with the right abstractions |
| **SDD** (Specification-Driven Development) | Constrain, Interface | Constraint-first design, artifacts as contracts — ensures disciplined, traceable, right-sized design |
| **TDD** (Test-Driven Development) | Test, Implement, Verify, Optimize | Red-Green-Refactor cycle — ensures correctness and maintainability |

**How the original three innovations map:**

1. **Constraint-First Design** → SDD: Before any design, explicitly enumerate constraints (performance, scope, team, technology, operations, business). Every design decision traces back to at least one constraint. This is the mechanism that prevents over/under-engineering.

2. **Interface-First / Test-First Implementation** → TDD: Good interfaces are testable interfaces. Define contracts (Interface stage), then write tests against them (Test stage), then implement to pass (Implement stage). Interfaces serve as design checkpoints, drift prevention, and parallelization enablers.

3. **Artifacts as Contracts** → SDD: Each stage's output is the next stage's input contract. Breaking a downstream assumption requires going back to the producing stage.

4. **Domain-First Understanding** → DDD (new): Model the problem domain before jumping to technical solutions. Ubiquitous language ensures stakeholder terminology flows into code. Bounded contexts define clear module boundaries in the Design stage.

### Alternatives Considered

- **Module name `dev`**: Rejected — collides with the `dev` composite command
- **Module name `forge`/`techne`**: Rejected — not immediately recognizable as software engineering
- **Module name `eng`**: Close second, but `swe` is more specific and widely used
- **Command names from serpent metaphors** (coil, strike, shed): Rejected — not intuitive for software development context
- **Single `/dev` command with auto-depth**: Rejected — user wants individual step control plus turnkey option
- **`plan` as composite name**: Rejected — conflicts with Claude Code plan mode
- **`evolve` as tune composite**: Rejected — different register from spec/dev/ship; core `/evolve` is for plugin components, SWE tune is for user project code
- **`deliver` as ship**: Rejected — too long (7 chars) compared to other command names
- **`sprint` as meta-composite**: Rejected — Agile terminology implies time-boxed iteration, lacks feedback/upward-progression meaning that aligns with ouroboros philosophy

### Legacy Assets

32 pre-pivot skeleton files (commands/dev, agents/dev, skills/dev, templates/dev) archived to `dev/archive/`. These will be consulted during final verification for cherry-picking, but the SWE module is designed from scratch to avoid anchoring on outdated patterns.

**Consequence:** Module directory structure uses `swe/` namespace (`commands/swe/`, `agents/swe/`, `skills/swe/`, `templates/swe/`). Implementation will use ouroboros's own `/generate` command for dogfooding. Existing empty `commands/dev/`, `agents/dev/`, `skills/dev/`, `templates/dev/` directories remain available for future use or cleanup.

## DR-041: Artifact Lifecycle Management — Three-Tier Directory Structure

**Status:** active
**Date:** 2026-02-25
**Context:** SWE pipeline generates ~10 artifacts per spiral turn per component. After 3 turns on mdsearch, 22 files (276KB) accumulated in a flat `.swe/artifacts/` directory with no lifecycle management. Projected to 600+ files for a real project. Core module (knowledge, evaluations, decisions) has the same accumulation pattern. Brainstorm produced 14 ideas across 4 techniques; user discussion refined through 3 rounds.
**Decision:** Three-tier directory structure with full retention:

```text
.swe/
├── active/                              # Current spiral turn (bounded)
│   └── {NN}-{stage}.md                  # Numbered by stage order
└── record/                              # All completed turns (persistent)
    └── {package}/                       # Monorepo: package/service
        └── {NNN}-{task-slug}/           # Sequential within package
            └── {NN}-{stage}.md          # Full artifact set preserved
```

Key principles:

- **Keep everything**: Text files are cheap. No deletion. Git diff tracks changes over time
- **Monorepo-first**: Package-level grouping. Single-repo projects use one package directory
- **Order within package**: Turn numbering is scoped to package, enabling per-package engineering history
- **Self-maintaining**: tune/spiral auto-moves active → record on completion
- **Agent-efficient**: active/ is always bounded (max ~10 files). Agents look here for current context

**Alternatives rejected:**

- Delete After Tune (#6): User preferred retaining all artifacts for traceability
- Global sequential numbering: Doesn't scale for monorepos where packages have independent histories
- Component-only grouping (no order): Loses chronological decision flow within a package
- Manifest-driven discovery (#7): Coordination cost too high — every command must update manifest
- Git Notes (#14): Claude Code Read tool cannot access git notes natively

**Consequence:** All SWE commands must be evolved to write to `.swe/active/` instead of `.swe/artifacts/`. tune.md and spiral.md get an artifact archival phase. `scripts/artifact-lifecycle.sh` provides the mechanical operations. Core module lifecycle (knowledge, evaluations) is phased separately.

## DR-044: Safe Deletion — Project-Local `.trash/`

**Date**: 2026-02-26
**Status**: active
**Context**: During a red team audit, the AI directly executing `rm -f .tmp/*` caused permission issues due to missing settings.json entries. Attempted a full replacement with the system `trash` command, but: (1) cross-platform compatibility issues (macOS: `trash`, Linux: `trash-put`/`gio trash`, Windows: no native support), (2) macOS `~/.Trash/` is restricted by SIP for CLI access (list/restore not possible).
**Decision**: `scripts/safe-rm.sh` uses a project-local `.trash/` directory. (1) **delete**: moves files to `.trash/{timestamp}_{filename}` (platform-independent, always recoverable). (2) **list**: lists `.trash/` contents (supports pattern filtering). (3) **restore**: restores from `.trash/` to original location (exact/fuzzy matching). (4) **purge**: permanently deletes files older than N days (default 7). All scripts (session.sh, invoke-model.sh, regression.sh) call `safe-rm.sh` instead of `rm -f`. `Bash(rm *)` deny in settings.json. `.trash/` added to `.gitignore`.
**Consequence**: File deletion is recoverable on all platforms. No external dependencies. Avoids system trash permission issues. Blocks AI from using rm directly.

## DR-058: Spiral Evolution — Policy-Composed State Machine Architecture

**Date**: 2026-03-02
**Status**: active
**Context**: v0.14.7 achieved SWE 18/18 Level 4. The spiral (`/swe spiral`) is the meta-composite orchestrating Spec→Dev→Ship→Tune, but it's strictly linear: no backward transitions (despite declaring support), no parallel execution, no adaptive depth. Dogfooding on mdsearch (3 tasks) revealed: backward transition never used (even when needed — task 003 SAFETY-2 should have regressed to Design), Ship P2 issues deferred to next cycle instead of fixed, and users bypass the spiral for lightweight tasks. Research phase: Double Diamond (1st Research → Brainstorm → 2nd Research) produced 2 knowledge entries and 14 brainstorm ideas across 4 techniques.

**Research evidence base**:

- `docs/knowledge/ai-native-development-workflow-patterns.md` — 18 sources: state machine > DAG (LangGraph, Temporal, Val Town convergence), 3 orchestration primitives (sequential/parallel/iterative), checkpoint-based decomposition (Devin), mode consolidation pressure (OMC 9→fewer), "15-minute waterfall" as dominant AI-native micro-methodology
- `docs/knowledge/spiral-architecture-implementation-patterns.md` — 15 sources: LangGraph transition function table (`add_conditional_edges`), Temporal FSM with signals, LangGraph SQLite checkpoint schema (`parent_checkpoint_id` linked list), CI/CD cascade invalidation unsolved (Buildkite doesn't support it), ActionPlan probe boundary pattern, Dapr compensation pattern (unnecessary for pure artifact transforms)

**Decision**: Single state machine with composable transition policies, not multiple named modes.

### 1. Architecture: One State Machine, Three Initial Policies

The spiral becomes a state-machine orchestrator reading `spiral-state.json`. Composites (spec, dev, ship, tune) remain pure executors. Three named policy presets map to transition table configurations:

| Policy | Traversal Behavior | Use Case |
|--------|-------------------|----------|
| **linear** | Forward-only with user-initiated regression. Current behavior formalized. Max 3 regressions. | Default. General-purpose tasks |
| **probe** | Light-depth exploration → confidence check → escalate or pivot. Hypothesis-driven iteration. | POC, spikes, exploratory tasks |
| **parallel** | Eligible stages run concurrently via worktree isolation. Ship.Security + Ship.CodeReview. | Large tasks with independent review stages |

Policies compose: `--policy probe+parallel` = hypothesis testing with parallel probes. Interface: `--policy <name>` flag on `/swe spiral`.

**Rationale**: OMC had 9 modes that collapsed to fewer active ones. Named modes proliferate. A single state machine with configurable transition tables avoids sprawl while named presets maintain discoverability. Research shows all orchestration patterns reduce to 3 primitives (sequential, parallel, iterative) — policies compose these primitives.

### 2. Transition Function Table

The Decision Matrix in spiral.md (14 branch conditions) is already a transition function table in prose. Externalize to JSON policy files:

```json
{
  "policy": "linear",
  "transitions": {
    "spec_composite": {
      "on_success": "spec_dev_transition",
      "on_failure": { "retry": "spec_composite", "abort": "terminated" }
    },
    "dev_composite": {
      "on_success": "dev_ship_transition",
      "on_failure": { "retry": "dev_composite", "regress": "spec_composite", "abort": "terminated" }
    }
  }
}
```

Pattern from: LangGraph `add_conditional_edges(source, router_fn, {label: target})`.

### 3. State Persistence: `spiral-state.json`

Single JSON file in `.swe/active/`. Schema refined from LangGraph checkpoint model and WorkflowEngine.io process instance, simplified for single-user file-based environment:

- `stages`: flat dict with per-stage status enum (`pending|running|completed|invalidated|stale`)
- `checkpoints`: array with parent links (LangGraph `parent_checkpoint_id` pattern)
- `transitions`: append-only event log for auditability
- `regression_count` + `max_regressions` as circuit breaker (OMC pattern)

### 4. Checkpoint-Rewind with Cascade Invalidation

Backward transition = restore checkpoint N, re-execute from there. Artifact versioning via `.swe/active/.versions/{NN}-{stage}.v{N}.md`.

Cascade invalidation algorithm (novel — CI/CD systems don't support this natively):

1. When Stage N artifact is re-versioned, traverse Selective Load Matrix in `artifact-contracts.md`
2. Downstream stages with "Required" dependency → invalidated (must re-execute)
3. Downstream stages with "Optional" dependency → stale (re-evaluate, may preserve)
4. Present invalidation list to user for decision (human-in-the-loop)

### 5. Probe Execution (deferred to v0.15.0-phase-2)

Probe artifacts in `.swe/active/.probe/` (file-system isolation). Promotion = copy to active. Discard = cleanup. Requires spiral command to support stage-level re-entry (not just composite), which is a larger refactor.

**Deferred because**: linear policy with regression (items 1-4) delivers the core value — backward transitions and state tracking. Probe builds on this foundation. Implementing both at once risks over-engineering before dogfooding validates the state machine.

### Implementation Order

| Phase | Scope | Files | Effort |
|-------|-------|-------|--------|
| **Phase 1** | State file + linear policy | `spiral-state.json` schema, `spiral.md` refactor, `artifact-lifecycle.sh` extension | Medium (3-5 sessions) |
| **Phase 2** | Checkpoint-rewind + cascade | `.versions/` convention, cascade algorithm, state file checkpoint entries | Medium (2-3 sessions) |
| **Phase 3** | Parallel policy | Ship.Security + Ship.CodeReview via TeamCreate + worktree | Small (1-2 sessions) |
| **Phase 4** | Probe policy | `.probe/` directory, stage-level re-entry, confidence thresholds | Large (4-6 sessions) |

New reference files: `skills/swe/methodology/references/spiral-state.md` (state schema, transition rules), `skills/swe/methodology/references/stage-capabilities.md` (dependency graph, parallelism matrix). Template: `templates/swe/spiral-state.json`.

**Alternatives considered**:

1. **Multiple named modes (linear, swarm, probe as separate commands)** — 7 paradigm candidates from preliminary analysis. Rejected: mode consolidation pressure (OMC evidence), maintenance burden of parallel codepaths, policy composition impossible with separate commands.
2. **Full state machine library (XState, Python transitions)** — Rejected: Claude Code plugin runs in markdown command files, not executable code. JSON transition tables achieve the same behavior with no runtime dependency.
3. **Probe as default (always try cheap first)** — Rejected: unpredictable execution cost, users lose budget predictability. Better as opt-in policy.
4. **Confidence thresholds at all gates** — Rejected: confidence calibration is hard, no production examples of "probe then promote" in AI coding pipelines. Start with binary gates, evolve to confidence when dogfooding provides calibration data.
5. **Eliminate Ship composite (fold into Verify)** — Rejected: Ship has distinct ownership (reviewer agent), severity classification (P1/P2/P3), and user checkpoint. Per-composite depth `--depth H:Light` already minimizes Ship ceremony.

**Consequence**: v0.15.0 implements Phases 1-2 (state machine + linear policy + checkpoint-rewind). Phases 3-4 are v0.15.5+ based on dogfooding results. Methodology SKILL.md gains "Fixed stages, variable traversal" principle and Modes section. `docs/designs/v0.15.0-spiral-analysis.md` preserved as research artifact.

## DR-059: Probe as Default Policy — Orthogonal Depth × Policy Model

**Date**: 2026-03-02
**Status**: active
**Context**: v0.15.0 delivered the state machine with `linear` as the only policy. Planning v0.15.1 (probe policy), UX review revealed the spiral's flag surface was already complex (`--fast`, `--depth`, `--policy`), and adding `--policy probe` as opt-in would increase cognitive load. The depth and policy flags were conceptually coupled — `--fast` is a depth shortcut but behaves differently under different policies.

**Decision**: Make `probe` the default policy and restructure depth/policy as orthogonal dimensions:

- **Depth** (how deep): `--fast` (Light) / default (Standard) / `--deep` (Deep, new) / `--depth S:Deep D:Std ...` (per-composite)
- **Policy** (how to traverse): `probe` (default) / `linear` (opt-in) / `parallel` (future)
- Depth controls the escalation target, policy controls the traversal behavior. Each dimension is independent.

**Rationale**:

- Probe as default means the simplest invocation (`/swe spiral "task"`) uses the smartest traversal — Light first, escalate only if needed
- `--fast` semantics unchanged from user perspective (still "quick"), but now explained as "Light target where probe degrades to direct execution"
- `--deep` added as symmetric counterpart to `--fast` — `--depth Deep` shortcut
- `--policy linear` for users who want direct execution without probing
- Confidence check is user-driven (no auto-threshold) — DR-058 rejected automated confidence as uncalibrated

**Alternatives rejected**:

1. **Probe as opt-in (`--policy probe`)** — adds a flag for the recommended default behavior; users who don't know about it miss the benefit
2. **Auto-escalate** — requires quality criteria that don't exist yet; deferred until dogfooding provides calibration data
3. **Named presets (`--preset quick/explore/thorough`)** — replaces two orthogonal dimensions with a flat list; less composable

**Consequence**: Default spiral behavior changes from "direct Standard" to "probe Light → escalate to Standard if needed". `--policy` flag rarely needed in practice. `--deep` flag added. DR-058's phased plan (Phase 3: probe) delivered as v0.15.1 with the UX simplification.

## DR-060: SWE Pipeline Parallelism — Stage Parallel + Multi-Model

**Date**: 2026-03-02
**Status**: active
**Context**: v0.15.5 was originally planned as "Parallel Policy" — a spiral-level `--policy parallel` with worktree fan-out/fan-in across composites. Analysis revealed this was infeasible: the SWE artifact chain is strictly sequential (each composite depends on the previous composite's output). However, independent sub-stages within composites exist: Ship has Security Review + Code Review (both read implementation artifacts independently), Tune has Improve + Retrospect (different file domains — source code vs. artifact chain). Additionally, core commands have mature `--multi` (11+ commands) but SWE pipeline had zero multi-model support.

**Decision**: Two independent parallelism axes, both composite-internal:

- **Stage parallelism** (speed, always active): At Standard+ depth, independent sub-stages run as parallel Tasks. Ship: Security Review ‖ Code Review. Tune: Improve ‖ Retrospect. No opt-in needed — reviewer Tasks are read-only, Improve/Retrospect touch different files.
- **Multi-model parallelism** (quality, `--multi` opt-in): Ship adds Codex security + code reviews alongside Claude (2×2 grid). Tune adds Codex evaluator alongside Claude evaluator. Finding union + severity consensus for reviews; priority consensus for evaluation targets.
- **Spiral-level `--policy parallel` removed** from the roadmap. Stage-level parallelism is composite-internal, not a traversal policy.
- **`--multi` relayed by spiral**: `spiral --multi` passes the flag to Ship and Tune composites.
- **P1 severity disputes resolve to P1** — false negatives (missing a critical finding) are more costly than false positives.

**Alternatives rejected**:

1. **Spiral-level `--policy parallel`** — artifact chain is strictly sequential; composites cannot run in parallel
2. **Auto-parallelism without flag** — debugging multi-model consensus issues requires explicit opt-in to isolate
3. **Multi-model for all composites** — Spec (analyst) and Dev (implementer) don't benefit from model consensus; code synthesis is single-model

**Consequence**: DR-058's `parallel` policy row removed from the traversal policy table. Ship and Tune composites gain `--multi` flag. Three new relay response schemas (SR, CR, SQ) and SWE relay prompt templates added. Stage parallelism is transparent — users see faster Ship/Tune without any flag changes.

## DR-061: Team Spiral — Pipelined Composite Execution

**Date**: 2026-03-02
**Status**: active
**Context**: Track A complete (v0.15.0 linear → v0.15.1 probe → v0.15.5 stage parallelism). All three are single-agent policies — the main conversation orchestrates composites sequentially via Skill tool. Track B introduces multi-agent collaboration: multiple persistent specialists execute composites concurrently, with cross-perspective review and dynamic backtracking. Key questions: entry point (new command vs policy flag), team topology, composite invocation model, and how gates work in a pipelined context.

**Decision**: `--policy team` on existing spiral.md. Director (main conversation) + 3 persistent specialist teammates (Shaper, Builder, Critic) spawned via Agent tool with `team_name`. Pipelined composite execution with cross-review:

- **Pipelined execution**: When a composite completes, the next composite and a cross-review of the just-completed composite start simultaneously. Gates auto-check artifact existence rather than blocking for user approval. Only the P1 gate after Ship is blocking.
- **Specialist composite invocation**: Specialists invoke composites directly via Skill tool (verified: teammates have full access to all 22 ouroboros skills). Director handles state machine updates exclusively to prevent race conditions.
- **Cross-review protocol**: After Spec, Critic reviews architecture/constraints/interface for quality. After Dev, Shaper reviews implementation for domain correctness. Findings classified as P1 (contract-breaking → backtrack) or P2/P3 (non-blocking → deferred to Tune).
- **Dynamic backtracking**: Cross-review P1 triggers backtracking. Director evaluates downstream progress — if Builder is in early stage (Test), halt and revise; if late stage (Implement+), continue and flag for urgent fix in Tune. Reuses existing regression protocol (checkpoint → cascade → restore).
- **Director relay checkpoint**: Composite Review content sent to Director via SendMessage, Director shows to user. Timeout auto-proceed if no user response.
- **Collaborative Tune**: All 3 specialists contribute perspectives (domain insight, implementation challenges, quality findings) before Director invokes Tune.
- **Team topology**: Shaper owns Spec + cross-reviews Dev output. Builder owns Dev + does codebase pre-analysis during Spec. Critic owns Ship + cross-reviews Spec output + early security scan during Dev. Naming deliberately differs from composite-internal agents (analyst/implementer/reviewer) to distinguish role layer from execution layer.
- **State machine v2**: `spiral-state.json` gains `team` section (specialist status, cross-review tracking) with version bump to 2. Backward-compatible — non-team policies use version 1 schema.

**Alternatives rejected**:

1. **Separate `team-spiral.md` command** — mode proliferation (OMC research warning). Single entry point with policy flag is more composable and discoverable.
2. **Director-only Skill invocation (advisory specialists)** — tested in design phase; no genuine collaboration, just "sequential pipeline with background readers." Contradicts the goal of real concurrent engineering.
3. **Stage-level pipelining (primitive commands)** — deferred to v0.16.5. Composite-level pipelining provides meaningful overlap with manageable orchestration complexity. Stage-level adds mid-composite intervention but requires message checkpoints between every stage.
4. **Specialist agent definition files** — unnecessary. Existing agents (analyst/implementer/reviewer) are composite-internal executors invoked by Task tool. Team specialists are persistent teammates with different lifecycle — spawned via Agent tool with team_name, prompted inline.
5. **Separate team state file** — synchronization burden with spiral state. Single `spiral-state.json` with conditional team section avoids dual-source-of-truth.

**Consequence**: spiral.md gains third traversal policy. Team execution details delegated to `references/team-execution-pattern.md` (~250 lines). State schema version bumps to 2. Existing `linear` and `probe` policies unchanged. v0.16.5 extends to stage-level pipelining, team+probe composition, and cross-turn learning.

## DR-062: Team Spiral Advanced — Stage-Level Pipeline, Bridge Agent, Cross-Turn Learning

**Date**: 2026-03-02
**Status**: active
**Context**: v0.16.0 delivers composite-level pipelining (Director + 3 Specialists). Three limitations remain: (1) composites are black boxes — Specialist calls `/swe spec` and 4 stages run internally with no mid-composite intervention; (2) turn-to-turn learning is disconnected — each spiral turn starts fresh without feedback from the previous; (3) only Claude agents can be specialists — no external model participation.

**Decision**: v0.16.5 introduces five features addressing these limitations:

1. **Stage-level pipelining**: Specialists invoke primitive commands individually (`/swe understand`, `/swe constrain`, ...) instead of composite calls. Message checkpoints between stages enable intra-composite cross-review (e.g., Critic reviews Design immediately, Builder starts Dev before Interface completes). Default for Standard+ depth; `--composite-level` or `--fast` reverts to v0.16.0 behavior.

2. **team+probe composition** (`--policy team+probe`): Combines team pipelining with probe's adaptive depth. Each specialist runs at Light depth first, then Director presents results with cross-review findings for user escalation decision. Cross-review findings inform the keep/escalate choice.

3. **Cross-turn learning**: Tune generates a `learning-delta.json` (depth calibration per-composite, team effectiveness metrics, process improvements). Next turn's Phase 2 loads the delta and presents advisory depth adjustments. `spiral-state.sh learning-delta save/load` actions.

4. **Generator-Critic loops**: At Standard+ depth in team policy, Design and Interface stages get 2-pass verification. Shaper generates → Critic reviews → P1 triggers revision → Critic re-verifies (max 2 iterations).

5. **Bridge Agent + selective routing** (`--route "understand=codex,implement=codex"`): External models (Codex/Gemini) participate as team members via Bridge Agent. Bridge Agent (`agents/swe/bridge.md`, model: sonnet) manages multi-turn MCP conversation with external model, handles all file operations on its behalf, and reports artifacts to Director. Subscription-based MCP servers (ChatGPT Plus via `codex mcp-server`, Google account via `gemini-cli-mcp`) — no per-token API costs. Circuit breaker: 3 consecutive failures → escalation to Director → fallback to Claude specialist.

**Key design choices**:

| Aspect | Choice | Rationale |
|--------|--------|-----------|
| Stage-level default depth | Standard+ only | Light depth: stage-level overhead exceeds benefit. `--fast`/`--composite-level` reverts to v0.16.0 |
| Bridge Agent model | sonnet | Relay/execution role — external model provides domain reasoning, Bridge provides tools. Lightweight model sufficient |
| MCP config | Subscription-based (.mcp.json) | User subscribes to ChatGPT Plus and Gemini — API keys would add per-token cost on top of subscriptions |
| `--route` vs `--multi` | Independent flags | `--multi` = one-shot relay for eval/review (invoke-model.sh). `--route` = stage delegation via Bridge Agent (MCP). Different mechanisms, different purposes |
| Learning delta format | Advisory only | Delta recommends depth adjustments; user decides. No auto-adjustment — avoids feedback loops |

**Alternatives rejected**:

1. **API key-based MCP** — rejected by user due to double-billing (subscription + API). Subscription-based MCP reuses existing ChatGPT Plus/Gemini Pro subscriptions.
2. **Bridge as general-purpose subagent** — too much autonomy. Bridge should relay decisions, not make them. sonnet model + structured protocol keeps it focused.
3. **Auto-escalation in team+probe** — deferred. User-driven escalation decisions maintain transparency. Future versions may add confidence-based auto-escalation.

**Consequence**: team-execution-pattern.md gains ~200 lines (Stage-Level Protocol, Probe Composition, Selective Routing, Bridge Integration, Generator-Critic). spiral.md adds `--route` and `--composite-level` flags. New files: `agents/swe/bridge.md` (120 lines), `.mcp.json` (subscription config). spiral-state.sh adds `stage-update` and `learning-delta` actions. tune.md adds learning delta generation.

## DR-069: Evaluation Infrastructure — Model Tracking + Dual Hash

**Status:** active
**Date:** 2026-03-06
**Context:** Evaluation result JSON did not record Codex model version/effort, making it impossible to distinguish the cause of score changes (file change vs model change). Accurate tracking was needed ahead of the `gpt-5.3-codex` to `gpt-5.4` transition.

**Decision:** Apply three infrastructure improvements simultaneously:

1. **Models structuring** — Change `multi_model.models` from a string array `["claude", "codex"]` to structured objects `[{"name": "claude", "model_id": "claude-opus-4-6"}, {"name": "codex", "model_id": "gpt-5.4", "effort": "xhigh"}]`

## DR-070: Evaluator File-Based Return — Context Protection

**Status:** active
**Date:** 2026-03-09
**Context:** In Mode B batch evaluation (8+ components), each background evaluator agent was returning the full markdown report (~3KB) as text, causing main context to explode. The Codex path was already file-based (`invoke-model.sh` returns JSON file + exit code only), but the Claude evaluator path was returning the full report.

**Decision:** Unify the evaluator agent's return pattern:

1. **Mandatory file output** — The evaluator always writes JSON to `.tmp/{session}_{idx}_claude_eval.json` and returns only a compact one-line summary: `"{component_path}: Level {N}, F:{a}/{b} Q:{a}/{b} E:{a}/{b} → {output_path}"`
2. **Mode branching removed** — Mode A/B/C/D all use the same pattern. Caller reads from file when detailed results are needed
3. **Write permission** — Added `Write(.tmp/*)` allow in `settings.json` to permit background agent file writes

**Consequence:** Context usage reduced from ~24KB to ~640B (97% reduction) for Mode B with 8 batches. Both Claude/Codex use the same file-based result + minimal return pattern. Write tool added to evaluator agent (JSON output only, scope boundary maintained).

## DR-071: Multi-Model Eval Hash — All Judge Models in Hash

**Status:** active
**Date:** 2026-03-09
**Context:** DR-069's `eval_hash` only reflected the external model (Codex) and did not include the Claude model ID. Even when the Claude model changed (e.g., opus-4 to opus-4-6), the eval_hash remained the same, making it impossible to track evaluation condition changes. For single-model evaluation, eval_hash was treated as equal to content_hash, so model information was not reflected in the hash.

**Decision:** Change the `regression.sh eval-hash` interface to variadic arguments:

1. **Variadic model arguments** — `eval-hash <file> <model[:effort]> [<model[:effort]> ...]`. All models used are passed as arguments
2. **Sort then combine** — Model arguments are alphabetically sorted before inclusion in hash input. Guarantees the same hash regardless of argument order
3. **Single model also explicit** — `eval-hash file.md claude-opus-4-6` (previously treated as identical to content_hash)

**Examples:**

- Single: `eval-hash doctor.md claude-opus-4-6`
- Dual: `eval-hash doctor.md claude-opus-4-6 gpt-5.4:xhigh`

**Consequence:** Any model combination is reflected in eval_hash, enabling accurate tracking of evaluation differences caused by model changes. Recalculated eval_hash for all 46 existing evaluation JSONs using the new method. DR-069's content_hash remains unchanged.

## DR-092: PII Masking Tiers + Private Tag

**Date:** 2026-03-18
**Status:** active
**Context:** 이름 외에도 전화번호, 이메일, 주소 등 개인정보가 자연어에 섞여 있음. "우리 팀장" 같은 역할 표현은 PII가 아니라 raw 데이터(번호, 주소 등)가 문제.
**Decision:**
(1) **Tier 1 — Regex PII**: 전화번호(`010-\d{4}-\d{4}`), 이메일, 주민번호(`\d{6}-\d{7}`), 계좌번호 패턴 → `[PHONE_1]`, `[EMAIL_1]` 등 카테고리별 토큰 치환. pa-mask.sh `--pii` 모드.
(2) **Tier 2 — Registered PII**: mask-map.json을 범용 PII registry로 확장. `kind` 필드: `name`, `org`, `address`, `phone`, `email`, `custom`. hash index도 kind별 지원.
(3) **Private Tag — 3단계 granularity**:
- 블록: `<!-- private -->...<!-- /private -->` — 여러 줄 감싸기
- 인라인: Tier 1 regex가 커버하므로 별도 인라인 태그 불필요. 정말 필요하면 `<!-- p: 내용 -->`
- 노트 전체: frontmatter `private: true`
(4) **Redaction 방식**: `[PRIVATE BLOCK]`으로 치환 (silent 삭제 아님). Claude에게 "여기에 내용이 있었지만 비공개"를 알림. `private: true` 노트는 shadow vault에서 stub 생성: `# [PRIVATE NOTE]\n\n이 노트는 비공개입니다.`
(5) **QMD 동작**: QMD는 로컬이므로 원문 인덱싱 정상 수행. MCP proxy가 결과 전달 시에만 name masking + PII masking + private block stripping 적용. `private: true` 노트의 QMD 결과는 제목 + `[PRIVATE NOTE]`만 반환.
(6) **Weaver 동작**: private-tagged 블록에서 entity 추출 안 함. `private: true` 노트에서 entity 추출 안 함. 단, private 노트로의 wikilink 관계는 유지 (entity는 존재, content만 미추출).
(7) **중첩 불허**: `<!-- private -->` 블록 중첩 금지. 단일 레벨만. frontmatter `private: true`와 블록 태그 동시 사용 시 frontmatter가 우선 (노트 전체 비공개).
(8) **Obsidian 호환**: HTML 주석이라 읽기 뷰에서 안 보임. Obsidian 자체 주석 `%%`와 역할 분리 — `%%`는 사용자 메모, `<!-- private -->`는 PA 프라이버시 마커.
**Consequence:** Tier 1-2 PII + private tag가 Phase 11b 범위에 포함. pa-mask.sh에 `--pii` + `--strip-private` 모드 추가. shadow vault sync와 QMD proxy에서 3중 마스킹 적용 (name + PII + private).

## DR-095: PA Phase 14 — Dynamic Activation + Life OS Loops

**Date:** 2026-03-20
**Status:** active
**Context:** Phase 13의 specialist runtime은 수동 생성/활성화만 가능. Area coverage signal 기반 자동 제안, review specialist 통합, deactivation lifecycle이 없음.
**Decision:**
(1) **Dual-anchor coverage signal** — specialist 제안에 profile anchor (core_areas) + activity anchor (ontology: goal/habit entity OR operational: 3+ work items) 이중 조건 요구. Profile anchor 없이는 제안하지 않음 — 사용자가 area를 선언하지 않으면 operational signal만으로 제안하지 않는다.
(2) **Suggested → active lifecycle** — survey에서 coverage signal 계산 → `status: "suggested"` stub 생성 → 사용자 interaction: create now (persona interview) / keep suggested / decline (30일 재제안 억제). Day/agenda에서는 non-blocking 알림만 (Phase 3.4), registry-level 변경은 survey만.
(3) **Deactivation 2-tier** — `source: "auto"` specialist만 hard deactivation (coverage drop 시 자동 inactive). `source: "generated"/"manual"/"default"`는 soft proposal only (survey/review에서 "일시 중지할까요?" 제안). 사용자 등록 specialist는 절대 자동 비활성화하지 않음.
(4) **Review capability-based filtering** — review Phase 3.5에서 specialist `capabilities` 필드와 horizon을 매칭: week(assess_today, habit_check), month(+carry_forward), quarter+(risk_scan, carry_forward). Irrelevant capability의 specialist는 건너뜀.
(5) **auto_state tracking** — `last_evaluated`, `last_declined_at`, `last_matched_at` 3개 필드로 activation lifecycle 추적. Day/agenda/review에서 `last_matched_at` 업데이트. 90일 무매칭 시 soft deactivation 제안.
(6) **Enrichment loop 제외** — specialist-insights.jsonl + survey catch-up profile feedback은 복잡도 높아 Phase 15로 연기. Phase 14 MVP는 specialist advice가 review에 포함되는 것까지.
(7) **Phase 3.4 non-blocking** — day/agenda의 suggested specialist 알림은 briefing 흐름을 끊지 않음. Phase 5에서 렌더링하고, 사용자가 보고 나서 응답.
**Consequence:** 1 new file (activation-signals ref) + 8 modified files. L4 3/3 consensus. Profile → ontology → specialist → day/agenda/review 루프 완성. Enrichment feedback은 Phase 15.

## DR-096: PA Phase 15 — Enrichment Loop (Specialist → Profile Feedback)

**Date:** 2026-03-20
**Status:** active
**Context:** Phase 14에서 specialist advice가 day/agenda/review에 포함되지만 ephemeral — 기록이 없어 패턴 감지나 profile 피드백이 불가.
**Decision:**
(1) **specialist-insights.jsonl** — JSONL append-only. 각 specialist consultation 후 status, confidence, surface, area_refs 스냅샷을 기록. 전체 observation 텍스트가 아닌 status + confidence만 저장 (패턴 감지에 충분, 파일 크기 최소화).
(2) **Same-day dedup** — area+local_date별 최신 1개만 streak 계산에 사용. Day+agenda 같은 날 실행 시 fake streak 방지.
(3) **Pattern types** — stable (3+ on-track), declining (3+ at-risk/needs-attention), shifted-up/down (이전 streak과 현재 status 비교). needs-watch는 declining에 포함. 3회 threshold: 2회는 우연, 5회는 피드백 지연.
(4) **Survey-only reader** — day/agenda/review는 writer만. Pattern reading은 survey Phase 5.5에서만. 소비 명령어에 "3주째 at-risk입니다" 메시지는 specialist advice와 중복.

## DR-106: Collaboration-First Dual-Model Protocol

**Date:** 2026-03-28
**Status:** active
**Context:** DR-028/029/030 define routing and invocation mechanics. DR-072 establishes Codex exec as the external model interface. During v2.0.0 Phase 0-3 implementation, a working collaboration pattern emerged: parallel independent planning → merge → direction-only delegation → autonomous execution → bounded peer review → selective user escalation. This pattern materially improved output quality and reduced user burden compared to single-model or micromanaged dual-model approaches. The pattern needs to be first-class and portable.
**Decision:** Collaboration is the default posture for non-trivial work when an external model is available. Default delegation level is `auto`. Controller (Claude) owns alignment, contract, merge, and review. Executor (Codex) owns delegated scope until review. Direction-only delegation by default — pass goals, constraints, boundaries, and verbatim invariants, not preferred implementations. Ownership handoff is clean — no mid-flight re-steering. Review is bounded to 2 rounds. User arbitrates only genuine ambiguity. Single-model remains correct for trivial, sensitive, or unavailable cases. Command-level `--multi` opt-in is unchanged and not superseded.
**Consequence:** New `skills/core/collaboration/` skill (SKILL.md + collaboration-protocol.md reference). CLAUDE.md operational adapter. AGENTS.md portable subset. Clear separation between collaboration methodology (this DR) and external-model routing mechanics (DR-028/030).

That masked legitimate quality misses in boundary cases, especially when Codex applied a stricter but rubric-defensible reading.
Self-evaluation leniency is a known risk in this pipeline, so the default should not favor the host model when evidence is contested.
**Decision:** Change the evaluation consensus default from Claude-wins-ties to stricter-score-wins.
For mechanical and structural criteria, the lower score wins unless the higher scorer cites direct satisfying evidence.
For qualitative criteria, the split remains unresolved, but the stricter score is still the default unless the models disagree on facts rather than thresholds.
When a single fallback verdict is required, use the more conservative outcome.
**Rationale:** Boundary cases should be treated as not-yet-passing because the split itself signals that the component is sitting on the rubric edge.
Codex's stricter readings are often defensible under the written criteria, and defaulting to stricter outcomes better resists self-evaluation leniency bias.
**Consequence:** `consensus-protocol.md` now defaults to stricter scores on splits.
Evaluation relay outputs are normalized before consensus so the controller compares one canonical shape instead of model-specific JSON variants.

# Feedback Learning — Behavioral Adaptation from Ledger Patterns

> Purpose: Reference for `personal-profiling` — defines how PA learns from user acceptance/rejection of proposals to adjust future behavior.
> This reference is standalone and can be consulted without the parent skill.
> For enrichment proposal rules, see `skills/pa/personal-profiling/references/enrichment-rules.md`.
> For ledger schema, see `skills/pa/trust-and-boundaries/references/ledger-schema.md`.

## Core Principle

**"Learn from what the user does, not what the user says."**

Ledger feedback (`accepted`/`rejected`/`modified`) is behavioral evidence.
It is stronger than inferred preferences but weaker than explicit user statements.
All learned preferences are proposal-only — never applied silently.

## Detection Pipeline

1. **Accumulate**: Commands record feedback entries in `assistant-ledger.jsonl` per the Feedback Recording Contract.
2. **Analyze**: `scripts/pa-feedback-analysis.sh analyze` computes per-command and per-action acceptance rates.
3. **Propose**: When patterns meet thresholds, generate preference candidates in `.pa/preferences-learned.json` with `status: "proposed"`.
4. **Surface**: During `/pa survey` Phase 5.6 (same checkpoint as enrichment), present one preference proposal per survey.
5. **Approve**: User confirms or rejects.
Only `status: "approved"` preferences affect command behavior.
6. **Apply**: Commands read `preferences-learned.json` during Phase 2.
Approved rules modify defaults (suggestion count, aggressiveness, verbosity).

## Detection Thresholds

| Condition | Threshold | Preference Kind |
|-----------|-----------|----------------|
| Command acceptance rate < 50% | 10+ feedback entries for that command | `frequency` — reduce suggestion count |
| 3+ consecutive rejections for same action type | streak detection (same as insight-accumulation) | `scope` — narrow suggestion scope |
| `too-many` tag appears in 30%+ of rejections | 5+ tagged rejections | `frequency` — reduce output volume |
| `wrong-target` tag appears in 30%+ | 5+ tagged rejections | `scope` — tighten targeting |
| Acceptance rate > 90% for a command | 10+ entries | `aggressiveness` — permit direct apply when posture allows |

Minimum global sample: 30 total feedback entries before any preference generation.

## Preference Kinds

| Kind | Effect | Integration Point |
|------|--------|-------------------|
| `frequency` | Reduce suggestion/output count | Command's output cap (e.g., link top-N) |
| `scope` | Narrow targeting | Command's entity/path filtering |
| `aggressiveness` | Permit or restrict direct writes | Command's posture decision logic |
| `verbosity` | Adjust output length | Chief-of-staff and scribe instructions |

## Preference Lifecycle

| Status | Meaning |
|--------|---------|
| `proposed` | Generated by analysis, pending user review |
| `approved` | User confirmed, active in command behavior |
| `reverted` | User disabled a previously approved preference |
| `expired` | Auto-expired after 90 days without reconfirmation |

## Anti-Patterns

| Anti-Pattern | Why Wrong | Correct |
|-------------|-----------|---------|
| Auto-applying learned preferences | Trust violation — user didn't consent | Always proposal-only |
| Modifying `soul.md` from feedback | Soul is identity, not behavior | Keep preferences separate |
| Learning from absence (no feedback) | Absence is neutral, not rejection | Only learn from explicit feedback |
| Applying preferences to explicit user requests | User override should always work | Preferences adjust defaults, not explicit commands |

## Threshold Rationale

| Threshold | Why |
|-----------|-----|
| 30 minimum total feedback | Smaller samples produce unreliable acceptance rates — a few bad days can skew results |
| 10 per command | Per-command rates need their own minimum to avoid noise from rare commands |
| 50% acceptance for frequency preference | Below half means more rejections than acceptances — a strong signal |
| 3+ consecutive rejections for streak | Consistent pattern, not random — same logic as specialist insight accumulation |
| 90 day expiry for approved preferences | User behavior evolves — preferences should be reconfirmed periodically |

## Common Pitfalls

| Pitfall | Why It Fails | Prevention |
|---------|-------------|------------|
| Auto-applying learned preferences | Trust violation — user never consented to behavior change | Always proposal-only, never silent |
| Learning from absence (no feedback) | User may have been busy, not dissatisfied | Only count explicit accepted/rejected/modified |
| Overriding explicit user requests | User typed a specific command for a reason | Preferences adjust defaults only, not explicit invocations |
| Modifying soul.md from feedback | Soul is authored identity, not behavioral tuning | Keep preferences in separate preferences-learned.json |
| Proposing too many preferences at once | Overwhelms the user | 1 preference per survey, highest-signal first |

## Consumer Reference

Commands that read `preferences-learned.json`:

| Command | Preference Kind | Effect |
|---------|----------------|--------|
| `link.md` | `frequency` | Cap suggestion count to recommended N (e.g., top-3) |
| `draft.md` | `aggressiveness` | Prefer proposal-only over direct write |
| `day.md` | `verbosity` | Adjust briefing length |
| `agenda.md` | `frequency` | Reduce unsolicited follow-up suggestions |

## Validation Checklist

- [ ] Feedback entries share `run_id` with their parent proposal entry.
- [ ] `feedback_tags` are from the allowed set only.
- [ ] Sample size checked before any preference generation.
- [ ] Per-command minimum (10) enforced alongside global minimum (30).
- [ ] Generated preferences have `status: "proposed"` — never `"approved"`.
- [ ] Approved preferences are inspectable in `.pa/preferences-learned.json`.
- [ ] Reverted preferences immediately stop affecting command behavior.

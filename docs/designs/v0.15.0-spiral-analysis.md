# Spiral Evolution — Design Analysis

> How do you make a linear engineering pipeline adaptive? This analysis explored 7 traversal paradigms and led to the state machine + probe policy design in v0.15.0–v0.15.1.

## Problem: The Linear Pipeline

The original SWE spiral followed a fixed sequence:

```
Spec (Stages 1-4) → [Gate] → Dev (Stages 5-8) → [Gate] → Ship → [Gate] → Tune
```

This worked for medium-complexity tasks but created friction in three areas:

| Problem | Symptom | Cost |
|---------|---------|------|
| No backward transitions | Gaps found in Stage 6 couldn't update Stage 3 | Workarounds accumulate in Tune |
| Fixed artifact cost | Light tasks produce the same 10-artifact chain as complex ones | Overhead deters adoption |
| No parallelism | Security review waits for code review to finish | Wall-clock time inflated |

### Evidence from Dogfooding

Three spiral tasks on a Rust project (81 tests total) revealed the pattern:

1. **Backward transition never used** — despite situations where it would have helped (a safety finding in Verify should have regressed to Design)
2. **Deferred items accumulate** — Ship findings that Tune can't address get pushed to the next cycle
3. **Lightweight bypass** — for simple tasks, users skip the spiral entirely and call individual stages

## 7 Traversal Paradigms

We analyzed seven approaches for making the pipeline adaptive:

| # | Paradigm | AI-Native Fit | Practicality | Selected? |
|---|----------|--------------|-------------|-----------|
| 1 | Linear with Regression | Medium | Very high | **v0.15.0** — state machine + regression |
| 2 | Risk-Driven Spiral (Boehm) | Medium-high | Medium-high | Deferred |
| 3 | Contract-First (V-Model) | Low | High | No |
| 4 | Appetite-Bounded (Shape Up) | Medium | Medium | No |
| 5 | Concurrent Team (Swarm) | High | Medium | **v0.16.0** — team spiral |
| 6 | Hypothesis-Driven (OODA) | Very high | High | **v0.15.1** — probe policy |
| 7 | Evolutionary/Tournament | Very high | Medium | Deferred |

Three paradigms were implemented across two releases. The key insight: these aren't mutually exclusive — they compose as traversal policies on a shared state machine.

### Linear with Regression (v0.15.0)

The existing pipeline extended with first-class backward transitions and state tracking:

```
1 → 2 → 3 → 4 → 5 → [gap detected] → back to 4 → 5 → 6 → 7 → 8
```

Required: regression cost tracking, cascade invalidation rules, circuit breaker (max 3 regressions).

### Hypothesis-Driven / Probe Policy (v0.15.1)

Test the riskiest assumption first. Light-depth exploration → targeted probes → confidence threshold → full implementation:

```
[Understand-Light] → [Constrain+Design-Light] → Hypothesis
  Loop: [Interface-targeted] → [Test+Implement as probe] → [Verify-targeted]
    Confirmed? → next hypothesis
    Refuted? → update understanding
  End: confidence threshold → full-depth implementation
```

AI agents excel at fast probe generation — this leverages their core strength.

### Concurrent Team (v0.16.0)

Multi-agent parallel collaboration:

```
t1: [Understand] → [Constrain]
t2:                → [Design] → [Interface]
t2':               → [Test draft]
t3:                             → [Implement] → [Verify] → [Optimize]
t3':                            → [Ship.Security]
```

Challenges: artifact conflict resolution, draft artifact protocol, coordination overhead.

## State Machine Design

The shared infrastructure that enables all three policies:

### State Model

A `spiral-state.json` file tracks execution across modes:

```json
{
  "mode": "linear|probe|team",
  "task": "...",
  "depth_plan": { "spec": "Standard", "dev": "Standard", "ship": "Standard", "tune": "Light" },
  "composites": {
    "spec": {
      "status": "completed",
      "runs": [{ "run_id": 1, "depth": "Standard", "stages": {...}, "artifact_versions": {...} }]
    }
  },
  "transitions": [],
  "regressions": [],
  "regression_count": 0,
  "max_regressions": 3
}
```

### Stage Dependency Graph

| Stage | Dependencies | Parallelizable? | Accepts Draft Input? |
|-------|-------------|-----------------|---------------------|
| 1 Understand | none | no | no |
| 2 Constrain | [1] | no | no |
| 3 Design | [2] | no | no |
| 4 Interface | [3] | no | no |
| 5 Test | [4] | yes | yes |
| 6 Implement | [5] | no | no |
| 7 Verify | [6,1,3,4] | no | no |
| 8 Optimize | [7,2,3] | no | no |
| Ship.Security | [6] | **yes** | no |
| Ship.CodeReview | [6,3,2] | **yes** | no |

Security Review and Code Review are independent — they can run in parallel (implemented in v0.15.5). Test can accept draft Interface Contracts, enabling speculative parallelism in team mode.

### Artifact Versioning

Regression preserves the current artifact and creates a new version:

```markdown
**Version**: 2
**Previous Version**: .versions/01-understand.v1.md
**Regression Source**: Stage 6 (Implement) — requirement misunderstanding discovered
**Changed Fields**: Success Criteria (added SC-4), Affected Components (added module X)
```

## Outcome

The three policies compose naturally:

- **Linear** (default): safe, predictable, good for well-understood tasks
- **Probe**: fast hypothesis testing, good for exploratory or risky tasks
- **Team**: parallel execution, good for large tasks with independent workstreams

All share the same state machine, artifact versioning, and regression handling. The policy choice affects traversal order, not the underlying infrastructure.
